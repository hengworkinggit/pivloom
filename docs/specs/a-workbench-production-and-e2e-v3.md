# A 方案正式接入与聚焦 E2E 规格

状态：2026-09-25，待实现和验收。用户已选定 A 方案；此前 `?variant=A` 页面只是本地可交互原型，不能作为正式模式完成证据。本文是本轮 `/to-spec` 的交付合同，既有 #29 负责单机全系统持久排队，不重复建立第二个队列实现。

## Problem Statement

现有正式工作台把多个版本控件、状态和检查信息堆在预览前；“新建项目”容易直接落入已有项目视图。用户选定的 A 方案展示了清楚的空白创作入口、左对话右预览、突出的当前版本和源码 hash、按需展开的历史/检查/发布，以及独立的模板和模型配置页，但它尚未接入真实身份、项目、Run、版本及发布数据。过去的长验收矩阵还使每个小改动都可能重复耗费真实模型和浏览器时间。

## Solution

用 A 方案替换正式 Web 页面：新建先进入空白创作页，项目列表优先呈现真实作品及现有截图，模板选择带入可编辑需求，模型设置沿用真实用户配置 API；工作台保持对话和大预览，真实任务状态、当前版本/源码 hash、历史/差异/回滚/检查/发布都从现有服务读取。演示原型中的假项目、假检查、假模型连接测试及本地内存状态不得进入正式模式。

每个可演示的页面切片都以对应浏览器 E2E 收尾。只对受影响模块运行该切片的正常路径、一个关键异常或权限边界、桌面与 390px 核对；事务/竞争场景使用真实 PostgreSQL 与受控执行器作集成补证。全部切片与 #29 达标后冻结一个 Web/API/GitHub 一致的提交，用新计算器和新 Canvas 贪吃蛇执行一次代表性真实模型主线，不对每张 Issue 重跑所有旧 E01–E42。

## User Stories

1. 作为新用户，我希望登录后先看到清楚的创作入口，以便直接描述想做的应用。
2. 作为已有项目的用户，我希望项目列表先展示自己的作品、截图和准确状态，以便迅速继续。
3. 作为用户，我希望点击“新建项目”得到没有旧对话和旧预览的空白页，以免误改旧作品。
4. 作为用户，我希望未提交的需求可编辑、刷新后恢复，以免导航中丢稿。
5. 作为用户，我希望从模板库查看六个实际模板的内容和示例，以便选择合适起点。
6. 作为用户，我希望使用模板只填入需求，确认后才创建项目或调用模型，以便保留修改机会。
7. 作为用户，我希望在页面保存、测试、编辑、删除模型配置，并选择默认模型，以便使用自己的服务。
8. 作为用户，我希望密钥输入和保存状态清楚且不被回显，以便确认配置而不泄露密钥。
9. 作为用户，我希望每次提交明确使用当前选定的模型，以便结果与配置对应。
10. 作为用户，我希望在左侧看到需求、回应和运行进度，右侧直接操作本次版本预览，以便判断成果。
11. 作为用户，我希望执行中刷新或重登仍返回同一任务和草稿，以免重复生成。
12. 作为用户，我希望资源满时看到真实排队、取消和后续自动执行状态，以免手工重发。
13. 作为用户，我希望当前版本号和短源码 hash 一眼可见，复制时拿到完整 hash，以便核对源码。
14. 作为用户，我希望在历史抽屉比较版本、查看完整源码与检查子项，以便理解每轮改变。
15. 作为用户，我希望回滚时明确目标版本，完成后对话基线、源码和预览一致，以便继续从旧版修改。
16. 作为用户，我希望主动选择正式发布，得到可长期访问的独立网址，以便分享作品。
17. 作为用户，我希望清楚区分开发当前版本、历史版本、已发布版本和平台部署 SHA，以免误读状态。
18. 作为用户，我希望在 390px 宽度下仍可发送需求、换模型、查看结果和版本，以便小屏使用。
19. 作为另一账号用户，我希望不能看到或操作他人的私有项目、源码、任务和预览，以便数据隔离。
20. 作为维护者，我希望每个模块有短而真实的验收证据，以便快速定位故障并继续并行开发。

## Implementation Decisions

- **复用现有边界。** 保留 Next.js、Fastify、Supabase Auth/PostgreSQL/Storage、Pi 和 OpenSandbox。页面通过已有鉴权 API、SSE、项目、模型、版本、回滚、预览和发布接口读写；不因换皮重建数据模型、执行器或第二套 agent loop。原型提供布局和交互参考，正式数据来自服务端。
- **创作入口。** “新建项目”先打开独立空白需求页。提交有效需求时创建新项目并绑定首次 Run；若创建成功但提交失败，页面保留项目和草稿并提供明确重试，不跳回某个旧项目。空输入、输入法确认和重复点击不创建重复 Run。进入已有项目始终保留该项目自己的对话、版本和预览。
- **模板。** 使用当前六个模板及其真实文案；模板详情可读，选择后把完整需求放入新建页输入框。模板本身不自动调用模型，用户可修改并显式提交。
- **模型。** 使用当前用户模型配置 API 和模型目录/端点发现；密钥由服务端加密保存，页面只呈现掩码及配置状态。工作台按 provider/profile/model 选择，Run 固定 model ID 和配置版本；不在浏览器本地持久化明文密钥。
- **A 工作台。** 桌面以对话和预览为主；窄屏切换两个主体。顶部保留项目、本人任务和账号入口；结果工具栏聚合预览/源码、当前版本、源码 hash、历史、检查、打开和发布。执行状态只在对应 Run 附近出现一次，长日志进按需抽屉。
- **版本语义。** 当前、正在查看的历史、回滚目标和已发布版本必须有不同标签。查看历史不切换 current、不修改对话基线；只有完成真实回滚后才更新 current。源码文件和 Check 必须绑定所显示 revision/sourceHash；平台 Web/API 部署 SHA 是另一类标识。
- **队列归属。** #29 持有接纳、调度、公平性、恢复和资源清理，也负责持久任务状态。A 工作台只消费真实接口，不通过前端定时重发或伪造“排队中”。#29 完成前可以独立完成其他页面，但最终联调必须覆盖 queued/running/cancelled/needs_action 等真实状态。
- **成熟开源复用。** 能直接调用已采用的上游能力时优先调用：Pi SDK、agent-browser、OpenSandbox、Supabase、现有 UI 组件。组件层参考 A 原型和现有设计系统。复制开源源码必须先核对具体文件许可、兼容性、归属及后续维护成本；Multica 的附加许可不允许作为“随便照抄”的来源。只移植能消除本项目维护代码的局部能力，不整套替换执行框架。
- **并行边界。** 项目/新建页、模板页、模型页、已有项目工作台可以在隔离分支并行实现，各自保有页面与相关测试。历史/检查/发布依赖工作台主体完成；最终验收依赖以上模块和 #29。合并时只解真实冲突，不因为 Issue 编号强制串行。

## Testing Decisions

测试从最高可观察界面进入，点击真实按钮并核对 API/数据库结果；截图、HTTP 200、产品自身 5/5 Check 各有范围，不能单独替代独立 E2E。沿用现有浏览器操作规程：优先 Codex 内置浏览器；独立会话能力不足时使用固定版本 agent-browser 并记录原因。生产 Reviewer 的沙箱浏览器与开发 QA 会话分开。页面级测试复用现有账号、项目和模板种子，集成测试复用现有 Vitest/真实 PostgreSQL 夹具；所有 fixture 明标，不能称为真实新模型生成。

| ID / 所属切片 | 浏览器动作与通过条件 | 独立补证与成本 |
| --- | --- | --- |
| A01 · 新建/项目列表 | A 账号登录，列表先见自身项目及保存的截图；点“新建”进空白需求页，旧对话/版本/预览不存在；输入草稿、刷新、合法提交后进入新项目；快速双击只得到一个首次 Run；390px 无横滚 | 同一项目/Run ID 的 API 记录；不必额外生成作品，首次真实生成可与最终 C0 共用 |
| A02 · 模板 | 看六个模板的详情；“使用”带完整需求到空白新建页，编辑、返回、再进入；未点击发送前 Run 数不变 | 模板 ID/需求内容对照；零模型调用 |
| A03 · 模型配置 | 创建、连接测试、设默认、编辑、删除测试 profile；重登后只显示掩码；工作台选定 profile 和模型，提交后展示所选项 | 用真实配置 API 和 owner 隔离检查；Run 的冻结 model/configVersion 在 C0 共用验证，不为本页另跑生成 |
| A04 · 工作台核心 | 打开已有成功项目，看对话/预览和当前版本/hash；提交一次需求，状态从 accepted/queued 到 running/terminal；执行中刷新仍为同一 Run；旧成功预览在新任务完成前仍可操作；390px 切换对话/预览不清稿 | UI↔API↔PostgreSQL 对照；可用受控执行器测状态投影，真实模型生成与 C0 共用且标明来源 |
| A05 · 历史/检查/回滚 | 打开历史和 Check 五组完整子项；查看旧版源码与可读 diff，页面明确“历史”与“当前”；实际回滚到已验收旧版，再核源码 manifest、Preview marker、current、对话基线同指目标 | 用已有两版测试项目做页面路径；回滚 CAS/并发由真实 PostgreSQL 集成测试补证。最终新计算器再验证从旧版继续增量 |
| A06 · 发布/部署标识 | 对测试项目显式正式发布，在无登录会话打开网址并操作页面；回收临时 Preview 后页面及资源仍可读；页面分别显示当前、已发布、Web/API SHA | 发布 marker/revision/hash 对照，Web/API 与所验 GitHub HEAD 一致；不因为查看历史自动更新已发布站点 |
| A07 · #29 队列 | 受控占满容量后用两个账号/项目提交，页面返回同一持久 queued 任务；刷新/重登仍在；取消一项不执行，释放容量另一项自动开始；任务列表只见本人 | 真 PostgreSQL 并发 claim、公平性、重启、沙箱回收测试在 #29；不在浏览器生成几十个真实应用 |
| A08 · 跨会话/账号 | 原会话退出重登，再用全新无存储浏览器登录 A；项目、对话、完整源码、版本和 Preview 逐项恢复。B 登录不能访问 A 的私有资源 | 现有 owner/session 集成测试核越权；不把同浏览器新标签当新会话。生成应用 localStorage 不承诺跨浏览器 |

**逐票关闭门槛。** 相关 A 用例通过、记录项目/Run/revision/hash/环境/部署 SHA、截图与实际结果；有异常处理的切片加一条有代表性的失败或越权路径。若更改了共享 API 或状态机，才额外跑受影响的集成测试。每票检查 1440px 与 390px 的本页主操作，但不重跑两个生成应用、全部生命周期故障或 E01–E42。失败仅重跑受影响路径及其直接依赖，保留原失败记录；`BLOCKED` 和 `NOT_RUN` 不写成通过。

**执行规则直接进入关单条件。** 每票在实现记录中写明直接复用的成熟开源包/仓库组件、实际调用边界和必要适配；有许可证附加条件的项目只参考设计，不直接复制。项目/新建、模型、已有项目工作台三条切片可以并行，模板只在新建入口落地后联通，版本/发布只在工作台主体完成后联通；不要用编号或全局浏览器锁人为串行源码、文案和 API 工作。Reviewer 用可观察进展、心跳和明确资源/预算边界判断停滞，不把固定 20 分钟当成所有规模任务的通过/失败标准；已保存候选和检查断点应尽量复用，不能因 QA 观察超时就从头生成。每票仅跑本模块 A 用例 + 一条关键异常/隔离 + 390px；最终 #37 才跑一次冻结 SHA 的计算器/蛇代表性主线，禁止把旧 15 轮复核或 E01–E42 全量复制到每票。

**一次发布候选真实主线。** 在已合并且冻结的同一提交上，用两个全新业务项目完成：计算器 C0 → 功能增量 C1 → 视觉/字段增量 C2 → 从 C2 回滚到 C1 → 基于 C1 做 C3；另生成要求 390px 适配的 Canvas 贪吃蛇 S0。无失败时共五次用户生成/修改提交，不把 Reviewer 的逐子项检查变成五轮生成。逐轮记录原 Prompt、真实模型调用/冻结配置、完整文件清单和 diff、版本号/hash、Preview marker、产品五组完整子项及独立必要操作；回滚后核 C3 的 base/plan 确从 C1 出发。蛇实际操作开始、方向/反向、暂停、吃食增长、自碰/墙碰、重开、同 origin 最高分，以及 390px 完整棋盘/控件。A08 用本轮项目补证；用户主动发布两件作品后以匿名独立会话验证长期 URL、资源与版本。末尾验证 Web SHA、API SHA、GitHub HEAD 一致。旧 #26–#28 的证据只作回归基线，不冒充这轮“全新项目”。

## Out of Scope

- 重写 Pi/Reviewer/调度框架，或为 A 方案引入第二套工作流系统。
- #29 的多机横向扩容、100 个真实模型任务压力测试和复杂预览分池。
- 每张 UI Issue 都执行计算器三轮、蛇全玩法及全部旧故障矩阵。
- 把临时 Preview 自动公开、把生成应用的 localStorage 业务数据称为平台云同步。

## Further Notes

过去 2–3 天的拖延有可复查原因：#26 的原始 Reviewer 曾 63 次工具调用、54 次点击但没有形成有效报告；后续遇到候选 TTL 早于 Run deadline、每行为 8 次动作上限和 CSP/浮点业务缺陷。#27 曾被固定 20 分钟 Reviewer 时限截断并给出 0/5 blocked，后又遇到 `BROWSER_ORIGIN_REJECTED`。#29 当前容量仅 2，资源满时拒绝请求，保留 Preview 也占名额。这些是执行/验收机制与资源瓶颈，并非单纯“测试太严格”。参考 [#26 过程](https://github.com/hengworkinggit/pivloom/issues/26)和 [#27 过程](https://github.com/hengworkinggit/pivloom/issues/27)。

改进规则：优先采用已核实的上游组件；真正独立的页面切片并行；按模块测其最高可观察用户路径，竞争和故障注入交给可重复的隔离集成测试；最终冻结版本只跑一次代表性跨模块真实主线。产品 Check 的五组/完整子项保留，不能通过减少断言取得通过，但不再把每个子项变成一次从头生成或整套 E2E。
