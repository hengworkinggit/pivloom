## 二、#29 收敛为单机持久排队

### 接收与执行分开

合法请求先持久化，返回任务标识与 `queued` 状态。容量不足仅影响何时执行，不再返回“资源已满，请稍后重试”让用户重新提交。网络重试使用原幂等键，刷新页面也读取同一任务。

排队期不创建沙箱、不发模型请求、不启动执行空闲超时、不计执行用量。资源到位后由统一调度模块原子领取任务、项目操作权与资源名额，再交给现有执行器。数据库未成功保存时不能显示“已进入队列”。权限、请求格式和明确版本选择的校验仍保留。

调度模块对调用方只暴露接收、取消和状态读取的接口；派发、租约、资源计数和重启恢复集中在实现内部。复用现有 PostgreSQL、执行器和 OpenSandbox，不把多节点扩容作为本轮前置。

### 全系统范围

生成、增量、失败重试，以及确实需要创建沙箱的预览恢复和回滚，共用调度与资源预约。任务类别不得通过另一入口绕过容量。

项目/源码/历史的普通读取、既有正式发布站点的访问照常执行。正式发布本身不额外创建沙箱时可以直接完成；若必须先恢复构建，则恢复步骤进入同一队列。正在发布的构建不能被回收。

### 调度与基线

- 同一项目的写操作串行。跨账号采用公平轮转；同一账号内按提交顺序选择可执行任务，持续有任务的单个账号不能独占派发。
- 全局资源受当前安全容量保护，可先采用单个执行任务的并发设置。等待任务只保存轻量数据。
- 同项目排队增量须明确承接关系：基于前序成功版本执行，并在开始时冻结真实 `baseRevisionId` 和需求计划。模型选择与配置版本在入队时记录，派发只能使用该选择；配置失效时保留任务并提示处理，不能默默换模型。不能因为入队时版本较旧而偷偷改成无关历史版本。
- 用户明确选择的历史回滚目标固定为该 revision/hash。前序失败、取消或发生无法自动判定的基线/配置冲突时，保留后续请求并显示可恢复原因；不把依赖失败当成功，也不阻塞其他项目。
- 排队取消立即落终态，不触发执行。运行中停止沿用现有中断及清理确认路径；只有确认资源释放，才能把名额交给下一项。
- 重启后恢复未开始的队列顺序。已执行工作沿用现有故障恢复规则，不无条件重放模型或工具；重复派发只能有一个有效领取者。

### 资源归还

有等待任务时，已完成、可安全回收的临时 Preview 不能一直占着执行名额。优先清理过期及被替代的预览；需要回收当前空闲预览时保留完整源码、版本、Check 和最后截图，并在页面明确显示“预览已休眠”。重新查看所需的恢复任务也排队。

不能回收正在构建、检查、回滚准备或发布读取中的沙箱。清理未确认仍占名额；不能只改数据库计数放行。已发布文件不属于这一回收范围。

现有前端作品的静态构建也可以进一步用于不占执行沙箱的私有预览；如采用此方式，必须继续保留鉴权，不能把未选择正式发布的项目公开。当前最小完成门槛是队列可以靠正常资源归还继续前进，而非先完成新的预览分池或多节点系统。

### 排队体验

提交后立即显示“已排队，资源可用后自动开始”与取消入口。工作台和项目列表指向同一任务；刷新、退出重登及新浏览器登录后状态一致，用户无需手动重发。只展示当前账号自己的任务和允许公开的总体排队信息。

队列位置只能来自实际调度状态；有可靠依据再显示预计等待时间。排队、运行、等待用户处理、停止中和失败需要清楚区分。“取消排队”与“停止当前任务”绑定各自任务 ID。

当前 [输入区](../../apps/web/src/components/api-workbench.tsx)仍用 `busy` 禁用发送，并提示先写草稿、结束后再发送。队列接入要区分“提交请求尚未确认”和“项目已有任务”：前者继续防重复，后者允许把下一条合法请求加入队列。排队期间已经成功的 current/Preview 仍保留，不能被待执行请求冒充为新版本。前端可以读取/订阅真实队列状态，但不能用定时重复提交模拟排队。

### 最小验收

1. 容量已用尽时，来自多个账号/项目的合法请求得到已持久化的排队任务；重复提交不重复创建，等待期间零模型请求、零新沙箱。
2. 释放名额后自动派发，不需要刷新或重发；执行数量不超配置，连续提交的一个账号不能饿死其他可执行账号。
3. 刷新、重登、API/调度进程重启后队列仍在；两个领取者竞争不会重复执行同一项。
4. 排队取消不启动任务；运行中停止在清理确认后让下一项前进；确认失败的资源不会被提前复用。
5. 同项目连续请求、旧版本回滚、前序失败/取消的基线语义正确；显式历史目标不会被换掉。
6. 生成、恢复预览和回滚共享容量；两个保留预览占满资源时，正常回收能够推进队列，源码及正式站点保持可访问。
7. 真实页面能完成提交、排队、自动开始、取消及重登恢复。调度竞争用真实 PostgreSQL 和受控执行器隔离测试；真实业务主线沿用 v3 的两个新应用，不要求在这台机器生成100个应用或搭建两节点压测。

## 三、UI 信息层级

沿用现有品牌、字体基础和蓝紫色主色，优先调整工作台与项目列表。应用预览和用户对话是主体。

```text
项目名称                                      任务·2    账号
┌──────────────────┬──────────────────────────────────────┐
│ 对话             │ 预览 / 源码    当前 v12 · hash ⧉     │
│                  │                历史  检查  打开  发布 │
│ 用户需求         ├──────────────────────────────────────┤
│ 简短进度与结果   │                                      │
│                  │             应用预览                 │
│                  │                                      │
│ 排队 / 运行状态  │                                      │
│ 输入框           │                                      │
│ 模型       发送  │                                      │
└──────────────────┴──────────────────────────────────────┘
部署 Web <sha> · API <sha>                 按需展开详细信息
```

上图是布局方案，不是已上线页面。历史、检查及执行记录在右侧抽屉按需查看，默认不挤占预览高度。

### 默认保留在主界面的信息

- 顶部保留返回、项目名、自己的任务入口和账号菜单。
- 结果工具栏保留预览/源码、当前版本、短源码 hash 与完整复制、历史入口、检查状态、打开应用及发布。
- 当前版本与 hash 仍明显可见，取消大面积重复版本卡。源码 hash 与平台部署 SHA 使用不同标签。
- 当前执行或排队状态只出现一份，紧邻对应消息/输入区；正常连接的底层技术状态收进执行详情。
- 输入区保留文本、下一项任务选用的模型和发送。额度等次级信息放进模型菜单；影响提交时就地说明原因。
- Web/API 部署 SHA 移至轻量页脚，保留复制完整值和可核对性。

### 按需查看的内容

- **历史抽屉：** 版本列表、源码差异、来源对话、回滚。统一历史入口，去除下拉与重复列表同时占据首屏的布局。
- **检查抽屉：** 五组与全部子项、截图和未通过原因。主界面显示简短状态，结果不从产品中删掉。
- **任务/执行抽屉：** 自己的排队任务、当前运行阶段、模型/工具记录与错误详情。正常页面不常驻长日志和多个同义状态卡。
- 提交错误留在输入区，预览问题留在预览区，回滚问题留在历史抽屉；避免同一故障在多个位置重复铺开。

查看历史时明确显示“历史 vN；当前 vM”，不能把历史 hash 当当前 hash。回滚仍通过明确的目标操作改变 current；正式发布继续由用户主动选择。打开抽屉或查看日志不应重新创建沙箱、重载预览或清空草稿。

### 项目列表与小屏

已有项目的用户优先看到自己的项目：截图、名称、一个准确状态、更新时间。创建入口保持紧凑，模板移到新建流程；首次使用的空态可保留引导。复用现有持久化截图，不为了绘制卡片启动沙箱。

390px 下使用对话/结果切换，工具栏合理换行，避免把两栏硬压在一起；输入区、模型长名称和动作按钮均可见可用。版本/hash/发布入口仍可找到。平台工作台的窄屏验收与生成贪吃蛇自身的390px验收分开记录。

### UI 验收

- 桌面首屏能看见应用主体、输入框、当前版本/hash和发布入口。
- 历史查看、差异、回滚、源码复制、检查明细和正式发布的真实语义保持正确。
- 排队/运行/失败及取消入口绑定正确任务；切换项目和重登后仍一致。
- 390px 与长模型名称不造成横向溢出或按钮被挤出；切换面板保留草稿和当前应用状态。
- 保留已有键盘可达性、清晰标签和主题支持，用真实 API 状态验证，视觉截图不代替功能通过。

## 四、落地顺序

先确定并实现队列接口、持久化与派发，前端基于同一接口精简布局和呈现状态。两部分接通后执行各自聚焦的 E2E，再冻结提交运行技术复核 v3 的 C0/C1/C2/回滚/C3 与 Snake S0 主线，补正式发布与三处 SHA 一致性。

本次更新的是方案和 #29 要求，不能据此宣称排队或新版 UI 已完成。多节点扩容、复杂自动伸缩和100个真实模型任务不作为本轮交付门槛。
