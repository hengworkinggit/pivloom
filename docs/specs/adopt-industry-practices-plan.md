**实现落点的简化（下次直接照此，省掉接口改动）**：
"重试补齐 steps"**不必改 `replay-plan.ts` 或它的接口**。`apps/api/src/generation/review.ts` 里已经同时具备三样东西——**注入好的模型端口**（`createVisualJudgePort(input.modelConfig, signal)`）、**`input.handoff.plan`**、以及**调用 `runScriptedPlan` 的位置**。因此补全过程可以**完全落在这一个文件里**：

1. 在调用前扫一遍 `handoff.plan.behaviors`，找出**缺 `steps` 或 `assertions` 且 `evidence !== 'visual'`** 的行为；
2. 若有，用已有模型端口发**一次**请求，要求返回 `{ "<行为 id>": { steps, assertions } }`；
3. **合并时只取模型返回的 `steps`/`assertions`**，其余字段用原对象展开：
   `behaviors.map(b => ({ ...b, ...(patch[b.id] ?? {}) }))` —— **散文在结构上不可能被改动**（这正是那位执行者提出的保证，也是我复核时的第一件事）；
4. 补不出来（模型失败/返回不合法）→ **发一等事件并保持现有退回行为**，**不伪造 steps**；
5. 用补好的计划调用 `runScriptedPlan`。

**优点**：改动集中在**一个文件**、不触碰 `replay-plan.ts` 的签名与既有测试、也不碰任何判定标准。

**测试要点（两条，缺一不可）**：
- **掺假测试**：让桩模型**故意返回被篡改的 `expected`/`action`**，断言最终计划里这些字段**仍等于原计划**（证明"结构上不可改"，而不是"我们没改"）；
- **失败路径**：桩模型返回不合法时，断言**发出可观测事件**且**仍走原有退回**（不静默、不伪造）。

**⚠️ 实现前必须解决的一处耦合（我复核方案时发现，避免踩坑）**：
上面说"复用已有模型端口"时，**不能复用 `visualJudge`**。原因见 `apps/api/src/generation/review.ts:151`：

```ts
const visualJudge = input.modelConfig.supportsImages === true
  ? createVisualJudgePort(input.modelConfig, signal) : undefined;
```

**该端口只在"模型视觉已验证"时才创建。** 而"补齐 steps/assertions"是**纯文本**任务，与视觉无关。若复用它：
- **模型视觉未验证时，补齐会静默不发生**（端口为 `undefined`）→ 重试继续走模型路径；
- 这就成了一个**隐蔽耦合**：一个**文本**功能被**图像**能力门控，而且**失败是静默的**。

**正确做法**：为补齐单独准备一个**文本**模型通路（复用同一套请求机制与配置，但**不经过 `supportsImages` 门控**），或直接在该处按 `input.modelConfig` 构造一次请求。**并且**：端口不可用/调用失败时**必须发可观测事件**，不得静默。

**这条也说明"复用已有端口"这个建议下得太快**——我在上一轮批准它时没有核对它的创建条件，**这是我的疏漏，此处更正**。

### 2.1.2 **前置问题已答**：ref 载荷只有 `name` 与 `role`（2026-09-26 实测）

诊断通道生效——被 blocked 的 B40 判定正文里带上了字段清单：

```
STALE_BROWSER_REF: 第 6 步控件不唯一或已改变（role=button name="删除" 匹配 20 个）
请重新观察〔ref 字段：name,role〕
```

**即：浏览器的 ref 载荷只提供 `name` 与 `role`，没有任何层级/祖先/路径字段。**

**因此 Playwright 式的作用域无法用现有 ref 数据实现。** 三条路径的代价现在是明确的：

| 路径 | 可行性 |
|---|---|
| 从**树文本**推导包含关系（`browser.ts:161` 的 `tree` 有缩进结构） | 可行但脆弱，且树有长度上限、压缩后推导可能失真 |
| **序号谓词**（"第 N 个匹配"） | Playwright 官方**不推荐**（页面一变会点错元素）；与"宁可失败也不要猜"冲突 |
| **扩展浏览器适配器**，让每个 ref 带上祖先链 | 最接近 Playwright 语义；**需要改沙箱侧的观察实现**（该代码不在本仓库），成本最高 |

**决策要点**：B40 这类失败**不是应用的问题**——应用按可访问性惯例给每条历史的删除按钮命名为「删除」，**是步骤无法表达"哪一条"**。

### 2.1.3 **对 B40 的结论我改变了**：这首先是一个**可访问性缺陷**，其次才是技术问题

协调者当初问的那个问题——"删除按钮的可访问名称是「删除 2+3 = 5」这种带条目文本的形式，还是统一为「删除」"——**我当时答"统一为删除"**。现在看，**那个答案很可能是错的**，理由有两条，而且指向同一处：

1. **可访问性**：屏幕阅读器用户面对 **20 个都叫「删除」的按钮**，**无法分辨要删哪一条**。带条目文本的名称（"删除 2+3 = 5"）恰恰是**更好的**可访问名称——这也很可能就是协调者提出这个问题的原因。
2. **可验证性**：同一个歧义让**步骤无法唯一指认控件**（实测 `name="删除"` **匹配 20 个**）。

**所以这不是"要让验收机制适应应用"，而是"应用这里本来就该有更好的名称"。**

**这与业界一致**：Playwright 官方**不推荐** `first()`/`nth()`，而是要求"**构造一个能唯一标识目标的定位器**"——**在可访问名称层面消歧，正是它的首选做法**；我们调研里 Momentic 也把"用位置/包含/最近/第 N 个等线索消歧"放在**无障碍树**之后。

**因此对 B40 的处置应当是**：
- **计划侧**：该行为的期望改为要求**带条目文本的可访问名称**（唯一、可指认）；
- **应用侧**：按该期望命名（这同时修好了可访问性）；
- **而不是**去做"从树文本推导包含关系"或"序号谓词"这类基础设施改造。

**推广（这才是通用性教训）**：**当一条步骤无法唯一指认某个控件时，先问"这是不是应用的可访问性缺陷"，而不是先给验证机制加机制。** 前者修好了让所有用户受益，后者只是让机器绕过问题——**而我当初正是选了后者。**

## 批次一：回放内核对齐（进行中）

### 1.1 取消"截断 ⇒ 否决整页"
- **抄谁**：Playwright MCP——ref 失效只报 `Ref <ref> not found in the current page snapshot. Try capturing new snapshot.`，**只废该次调用**
- **抄什么**：截断不再阻止控件解析；只有真正无法唯一解析的那一个动作失败
- **落到哪**：`apps/api/src/runtime/replay.ts`（约 :247 的 `truncated` 前置抛错）、`apps/api/src/runtime/reviewer.ts`（约 :604 的 `latestRefsComplete` 前置抛错）
- **测试影响**：`an incomplete observation stops a control step instead of resolving refs from a partial tree`（钉旧规则，需按新语义改写）；`large observations declare truncation and expose only bounded valid refs visible in their tree`
- **保持**：`a stale control during the scripted pass is reported as STALE_BROWSER_REF, not a blocked candidate`——真正解析不到仍必须报 `STALE_BROWSER_REF`，不得降级成 blocked
- **状态**：进行中

### 1.2 失败后先重新观察一次再判定
- **抄谁**：Chrome DevTools MCP——"Always use the latest snapshot"；"If an element isn't found, take a fresh snapshot – the element may have been removed or the page changed."
- **抄什么**：解析失败 → 重新观察 → 重试一次；仍失败才报错。**重试次数显式且有上限**
- **落到哪**：同 1.1
- **状态**：进行中

### 1.3 名称匹配按 Playwright 默认
- **抄谁**：Playwright `getByRole`——"By default, matching is case-insensitive and searches for a substring, use `exact` to control this behavior."
- **抄什么**：默认**大小写不敏感 + 子串**（trim 空白）；需要精确时显式开 `exact`；**唯一性要求保留**（strict mode）
- **落到哪**：`resolveControl`（`apps/api/src/runtime/replay.ts`、`reviewer.ts`）
- **状态**：进行中

### 1.4 截断显式告知
- **抄谁**：browser-use——超出上限时在提示里追加 `" (truncated to 40000 characters)"`
- **抄什么**：截断写成给上层/模型的**明确标记**，而不是布尔否决
- **落到哪**：`apps/api/src/runtime/browser.ts`、`replay.ts`
- **状态**：进行中

### 1.5 refs 表与树文本解耦
- **抄谁**：Vercel agent-browser PR #1444——ref 绑**位置编号**会在 DOM 变化后**静默点错元素并返回成功**；必须绑**节点身份**
- **抄什么**：`!treeRefs.has(key)` 不再单独把整份观察判为不可信（refs 是浏览器权威控件清单，树文本只是证据文本）；**refs 超上限、元数据被截断这两支保留**为不可信信号
- **落到哪**：`apps/api/src/runtime/browser.ts`
- **测试影响**：`a longer ref or non-ref attribute cannot grant membership to an absent ref`
- **状态**：进行中

### 可复现查询

```sql
       jsonb_array_length(plan_json->'behaviors') AS behaviors,
       (SELECT count(*) FROM jsonb_array_elements(plan_json->'behaviors') b WHERE b ? 'steps') AS with_steps,
       state, coalesce(error_code,'') AS err
FROM nano.runs WHERE plan_json IS NOT NULL ORDER BY created_at DESC LIMIT 8;
```

```sql
-- 回放层的健康度（开始 / 退回 / 失败）
SELECT count(*) FILTER (WHERE payload_json->>'message' LIKE '脚本回放开始%') AS replays,
       count(*) FILTER (WHERE payload_json->>'toolName' = 'replay_fallback') AS fallbacks,
       count(*) FILTER (WHERE payload_json->>'toolName' = 'replay_error')    AS failures
FROM nano.run_events;
```

## 最后一块：退回落盘的粒度（整盘 → 逐条）

### 实测证据（2026-09-26，运行 `cd72fee6`）

```
12:00:24  脚本回放退回模型路径：35 项已编译，4 项不可编译
          （B32:missing-steps, B25:missing-assertions, B28:visual-evidence, B36:visual-evidence）
此后：模型路径动作数 = 130
```

- **35 条**行为已被确定性层跑完并产出真实判定（墙钟约 5 分钟）；
- 因剩下 **4 条**不可编译，**整次检查退回模型路径**，用模型一条条点（130 次动作），**走回约 30 分钟的慢路**；
- **这正是 ≤10 分钟无法达标的最后一处原因。**

### 业界从不这样做

| 产品 | 官方做法 |
|---|---|
| Stagehand | 缓存**逐次**命中→确定性；**未命中只对那一次调用**跑推理（"falls back to normal inference"） |
| Momentic | 命中→毫秒重放；**失配只重解那一步**（"只对本次运行生效"）；无法解决者 **quarantine 隔离** |
| Skyvern | **per-block 缓存**：只有变化的块回退 agent，其余照跑 |

**没有任何一家会因为 4/39 不可编译，就把 39 条全部重做一遍。**

### 应当改成（逐条落盘）

1. **`compiled` 非空时，永不整盘退回。** 已跑完的行为保留其真实判定；
2. **`visual-evidence` 类**：交给已有的视觉判定层（C 层，`visualJudge` / `judgeVisualBehaviours`）从像素判定并**合并**——这本就是 C 层的职责，不该触发整盘退回；
3. **`missing-steps` / `missing-assertions` 类**：该行为记 **`blocked`** 并在判定理由里写明原因（我们的 fail-closed 规则：**blocked ≠ passed**），**不整盘退回**；
4. **只有 `compiled` 为空（即全部不可编译）时**，才退回整次模型路径——那才是真正"没有确定性可用"的情形。

### 落地位置（已精确定位到行）

**`apps/api/src/runtime/replay-plan.ts:232`** —— 这就是实测中"35 项已编译、4 项不可编译 → 整盘退回"的确切来源：

```ts
return { kind: 'fallback', compiled: compiled.programs.map((program) => program.behaviorId), uncompilable: compiled.uncompilable };
```

同一文件 `:203-206` 已有正确的先例可循：当**全部**不可编译项都是 `visual-evidence` 且存在视觉判定端口时，它会**不退回**、直接走视觉判定（`judgeVisual`）。要做的就是把这种"能落盘就落盘"的判断从"全部是视觉项"扩展到"**只要有已编译程序**"：已编译行为的判定保留、视觉项交给视觉判定、其余不可编译项记 `blocked` 并写明原因；`compiled.programs.length === 0`（`:205-206`）时才整盘退回。

### 落地时唯一需要先读清楚的细节（顺序问题）

`:229-232` 那段退回的**原始理由写在注释里**："模型路径对整个计划负责，所以部分编译的计划不能提交部分结果"——**该理由在"模型路径是唯一路径"的时代成立，在分层设计下不成立**（业界做法相反：能落盘就落盘，落不了的逐条隔离）。

改法是：删掉这个提前退回，改为**为每个不可编译项填入一条 `blocked` 判定**（理由写明 `missing-steps` / `missing-assertions` / `visual-evidence`），然后让后面的组装流程照常进行。

**但必须先读清楚组装路径中视觉判定的写入顺序**：`visual-evidence` 的判定项是在这段退回**之后**才被塞进 `run.items` 的（来自 `captures` / `verdicts`）。因此填 `blocked` 时必须避免与视觉项互相覆盖——两种可行做法：

1. **只为本就非视觉的不可编译项填 `blocked`**（`visual-evidence` 交给后面的视觉判定），这是最小改动；
2. 或为所有不可编译项填，但**确保视觉判定随后覆盖**（需确认覆盖语义，风险更高）。

**推荐第 1 种**：改动最小，且不会触碰视觉判定既有行为。落地时相应新增测试：**"混合不可编译（既有视觉项也有缺步骤项）时，已编译行为保留真实判定、缺步骤项记 blocked 并写明原因、且不整次退回模型路径"**。

### 落地位置与影响（其余）

- **位置**：`apps/api/src/generation/review.ts` 中处理 `scripted.kind === 'fallback'` 的分支（当前无条件退回 `modelPath()`）；以及 `replay-plan.ts` 中 `uncompilable` 的产出与 `runPrograms` 结果的合并处。
- **不改**：判定标准、守卫、fail-closed 规则、五组完整性要求。
- **完成后应当出现的可观测结果**：不再出现"35 项已编译 → 模型路径 130 次动作"；取而代之是"35 项确定性判定 + 4 项带原因 blocked/视觉判定"，**且墙钟保持在数分钟内**。
- **验收**：一次真实运行，给出 **A+B 实测墙钟**；若仍有 blocked 项，则是"该行为确实无法确定性验证"的**诚实结论**，而不是整次滑回慢路。

### 为什么这是"通用性"的关键

通用应用里**一定有**部分行为无法确定性编译。**如果一条不可编译就整盘退回，那么确定性层在通用应用上等于不存在**——这既是性能问题，也是产品是否可用的分水岭。

## 2.1 作用域定位的前置问题（已勘察，必须先回答）

**实测证据**：运行 `c064aa39` 的 B40 —— `STALE_BROWSER_REF: role=button name="删除" 匹配 20 个`。这正是"每行一个同名控件"的通用问题，Playwright 的官方解法是**先缩小作用域再定位控件**（`getByRole('row').filter({hasText:'...'}).getByRole('button', …)`）。

**但照抄它在我们的实现里行不通，原因是数据结构不同**：

- **Playwright 有真实 DOM 树**，所以 `filter({hasText})` 能在子树里找。
- **我们只有扁平表**：`apps/api/src/runtime/browser.ts:17` 的 `refs: Record<string, { role?: string; name?: string }>`——**每个 ref 只有 role 与 name，没有任何父子/祖先关系**。

因此"作用域"要先解决**数据从哪来**，三条候选路径（需先确认浏览器协议能提供什么）：

1. **让浏览器适配器为每个 ref 暴露祖先链**（最接近 Playwright 语义；取决于底层协议是否给出层级——**未确认**）；
2. **从树文本推导包含关系**（`browser.ts:161` 的 `tree` 有缩进/括号结构）：可行但脆弱，且树会被压缩（`:161` 的上限），压缩后推导可能不可靠；
3. **退一步的消歧谓词**：不引入层级，而是让步骤能表达"在匹配到的第 N 个"或"名字包含某段文本的那个"。**但注意 Playwright 官方明确不推荐 nth 类做法**（页面一变会点错元素，见本文件批次一 1.3 的出处），所以这条要与"宁可失败也不要猜"权衡。

**结论**：2.1 不是"照抄一行 API"，而是**先确认观察数据能否承载作用域**。**在回答这个问题之前不动手**——否则很可能做出一个在压缩树上偶发失灵的"作用域"，那比现在诚实报 blocked 更糟。

## 发现的真问题：**重试路径绕过了确定性层**（2026-09-26，运行 `80f41c5e`）

为验证"同一计划跑两次判定是否一致"，我用 `submit-retry` 对 `9818ed23`（计划 40/40 带 steps）发起重试。结果**实验本身不成立，但它撞出一个更重要的问题**：

|---|---|
| 该重试运行跑到 8.2 分钟时 | 仍在 `verifying/review` |
| 该运行的最新事件 | **"检查者已收到实际模型流式内容"** ← **模型驱动路径** |
| **该运行的回放完成事件数** | **0** ← **A 层完全没有执行** |

**结论**：**重试/复用已封存候选的路径，不经过 A 层（确定性回放），直接进入模型驱动评审。**

### 为什么这很重要

1. **操作者在检查失败后最常做的就是重试**——而**重试拿不到 7 分钟的验收**，走的是那条历史约 30 分钟的模型路径。**"验收段 ≤10 分钟"对重试并不成立**，这是一条**未达标的主要路径**。
2. 它也**解释了本会话最早期的一个困惑**：那时所有 `submit-retry` 运行都是 `带 steps=0`、从不触发回放。我当时归因为"复用了旧计划"——**真正的解释是"根本没有走 A 层"**。**我当时的结论是错的，此处更正。**
3. **因此我的复现性实验无效**（它比较的是两条不同路径），**结论作废，不作为证据。**

### 要查的事（下一步）

**A 层挂载在 `apps/api/src/generation/review.ts` 的 `runReview` 中**（`runReviewer` 之前）。那么重试路径是从**哪个入口**进入评审的？两种可能：

1. 重试走了**另一个入口**（例如专为"已封存候选复检"写的函数），该入口只调 `runReviewer`；
2. 或重试确实走 `runReview`，但 A 层因某个前置条件（如 `handoff`/`binding` 校验、或 `compiled.programs.length === 0`）而跳过。

**验证方法（便宜）**：一次重试运行里，看是否出现 `browser_steps` 事件（A 层的标志）。**本次为 0，故属第 1 种可能在先**——但需读入口代码确认。

**修好它之前，"验收段 ≤10 分钟"只在"新提交一次增量"这条路径上成立，不在重试路径上成立。**

### 更正上一条：重试确实进了 A 层，问题是**它复用的计划没有 steps**

上一条我写"重试路径绕过 A 层、A 层从未执行"。**那是错的，此处更正。**

**决定性数据**（运行 `80f41c5e` vs 原运行 `9818ed23`）：

| 观测 | 值 |
|---|---|
| 重试运行的计划 | **0/41 带 steps** |
| 原运行的计划 | **40/40 带 steps** |
| 两者是否为同一份计划 | **false** |

**自洽的解释**：

1. 评审只有**一个入口**（`apps/api/src/generation/executor.ts:356` → `runReview`），**A 层必然被进入**；
2. 重试**复用了一份旧计划（0 步）** → **可编译程序数 = 0**；
3. A 层遂在 `apps/api/src/runtime/replay-plan.ts:206` 走"整盘退回"，而该 return **在"脚本回放开始"事件之前** → **不会留下任何回放事件**；
4. 随后 `review.ts` 的 `modelPath()` 运行 → 观测到的"检查者已收到实际模型流式内容"。

**我的推理疏漏**：我把"回放事件为 0"直接当成"A 层没跑"的证据，**忽略了"整盘退回发生在事件之前"这条路径**。**最初的说法（复用了旧计划）是对的；上一轮的"更正"是错的。**

### 真正的问题与修法方向

> **重试复用的不是"最近一次带可执行步骤的封存计划"，而是一份更旧的（0 步）**，因此**重试永远走模型路径**（历史约 30 分钟），拿不到 7 分钟档的验收。

**修法方向**：让重试复用**最近的、带可执行步骤的封存计划**；或至少在复用到的计划 0 步时**明确告知/拒绝**，而不是静默滑回模型路径。

**验证方法（便宜）**：改完后发起一次重试，检查两件事——该运行的 `plan_json` 带 steps 数 > 0，且出现 `browser_steps` 的"脚本回放开始"事件。

## 第十六次实测暴露的结构性问题：**计划"预测控件名"这件事本身不可靠**（2026-09-26，运行 `f0df68be`）

我为修 B40（`name="删除"` 匹配 20）改了两件事：提示词要求"同名控件必须要求可区分的名称"（`3e35b23`，已部署）。随后的真实运行里，失败形态**变了**：

```
blocked B03/B05/B07/B08/B09 | STALE_BROWSER_REF:
  第 N 步控件不唯一或已改变（role=button name="=" 匹配 0 个）
```

**即：计划写的步骤是"点击名为 `=` 的按钮"，而应用里没有任何控件的可访问名称匹配 `=`。**（应用的等号按钮很可能叫"等于"之类。）

### 这与 B40 是同一根源的两面

| 现象 | 匹配数 | 原因 |
|---|---|---|
| B40：`name="删除"` | **20** | 名字**太泛**（20 条历史各一个） |
| 本次：`name="="` | **0** | 名字**猜错**（应用实际不叫这个） |

**共同根源**：**计划是在"还没看到页面"的时候写的，它对控件名的描述是预测。**

### 为什么这是"通用性"的核心问题

**通用应用里，任何按钮的名字都可能是开发者自由起的**（"等于"/"=" /"Equals"/图标按钮无文本……）。**让计划去把名字预测准，本质上不可靠**——这与目标里"未来不只是计算器"的担心完全一致。

### 业界正是因此不在计划里预测

| 做法 | 出处 |
|---|---|
| 定位器**在运行时对着活的 DOM 求值** | Playwright（其定位器是惰性的，每次动作前解析） |
| 用**无障碍树 + 多信号**在运行时解析，命中失败**只回退那一步** | Momentic（`step-cache` 失配 → locator agent 只重解这一步）；Stagehand（未命中 → 仅对该次调用推理） |
| 官方**不推荐**用序号兜底 | Playwright（页面一变会点错元素） |

### 因此剩下的一步（我之前漏掉的）

**把名称匹配改成 Playwright 的默认语义**：**大小写不敏感 + 子串**（trim 两侧空白），需要精确时才用 `exact`——**而不是我们现在的"逐字完全相等"**。

**注意这条只解决一部分**：若应用叫"等于"而计划写"="，**子串匹配也救不了**（"等于"不含"="）。**所以更根本的是"运行时解析"**（例如：该步骤交给一次模型解析，只解析这一步、只对本次运行生效——即 Momentic 的做法）。

**我此前只把"名称匹配过严"记在文档里而没有实现，这是我的漏项，此处明确。**

## C3 首次复测：**暴露容量问题（44 条行为只有 12 条带 steps）**（2026-09-26，运行 `4db448f3`）

| 指标 | 实测 |
|---|---|
| 验收段 | **1.3 分钟**（提前中止，非正常完成） |
| 计划规模 | **44 条行为** |
| **带 `steps` 的行为** | **12 条**（B01,B03,B15,B30,B31,B37,B40–B45） |
| 缺 `steps` 的行为 | **32 条** |
| 子项 | passed 3 / failed 0 / **blocked 41** |

### 关键：**不是截断**

我最初的假设是"输出被截断"（此前在 4096 上限上修过一次同类问题）。**数据否定了它**：带 steps 的 12 条**零散分布**（首尾都有），而不是"前 N 条有、后面全没有"。**所以是模型在一个 44 条的大计划里只给一部分行为写了步骤。**

### 这用实测证明了 E 项（P2 容量模型）的必要性

目标里 E 项要求：`capacity.ts` 成为**所有限额的唯一来源**，`limits(behaviours)=max(硬下限, 包络×余量)`，并做**跑前包络预检**（可分批就给分批方案，不能则带具体数字拒绝）。

**C3 这次就是"包络不够却没有预检"的实例**：44 条行为的计划**超出了协调者一次能可靠产出的规模**（步骤缺失率 32/44 ≈ 73%），而系统**照样提交了这次增量**，结果 41 条 blocked、验收段 1.3 分钟。

**因此**：
- **跑前预检**应在计划规模超出包络时**直接拒绝或给出分批方案**，而不是让它跑成一次必然失败的验收；
- 这也解释了此前多次运行中"带 steps 比例"忽高忽低（39/41、37/40、40/40、12/44）——**规模越大越不可靠**，与包络假设一致。

**待办（不改变任何判定标准）**：把 44 条这类规模的计划**按包络分批**（例如每批 ≤20 条行为），或**在预检阶段拒绝并给出具体数字**。

### 包络的实测边界：**落在 41 与 44 条行为之间**

汇总历次"计划带 steps 的比例"（这是包络最直接的观测指标）：

| 计划行为数 | 带 steps | 比例 | 验收结果 |
|---|---|---|---|
| **40** | 40 | **100%** | passed 35–37 |
| **41** | 39–40 | **95–98%** | passed 33–37 |
| **44** | **12** | **27%** | passed 3 / **blocked 41** |

**结论：可靠包络 ≈ 41 条行为；44 条即崩塌（缺步骤 73%）。**

### ⚠️ 明确：**"缩小计划条数"不是可接受的修法**

把计划压到 20 条确实能让 steps 比例回到 100%，**但那等于降低验收覆盖**——**违反"不减少子检查内容"的精神**。

**正确修法是"分批"（目标 E 项原本就写了"可分批则给分批方案"）**：
- 协调者**分多趟**产出计划（例如 G1–G2 一趟、G3–G5 一趟），**每趟都在 41 条以内的可靠包络里**；
