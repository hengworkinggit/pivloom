# 技术改造方案：评审容量模型与分层验证（v1）

状态：草案（待评审）
关联：GitHub #44（本文取代其机制部分，保留其原则）、#45、#37（验收在改造后进行）
分支：`feat/44-text-evidence`（B 层证据谓词已实现，17 个测试待逐个判定）

## 1. 问题陈述

过去 48 小时的所有失败是同一个形状：**限额是彼此独立的常数，工作量是计划规模的函数，没有任何环节在运行前验证二者的关系。** 于是限额只能在生产中被逐个撞出，且每次都被边界翻译成无法诊断的笼统文案：

| 失败 | 真实原因 | 诊断代价 |
|---|---|---|
| `TOOL_BUDGET_EXCEEDED` | 280 次调用上限 vs 45 条行为 | 数小时 |
| `AGENT_OUTPUT_INVALID` | 图片门控假设单工具轮 | 一夜 |
| `GENERATION_FAILED` | 证据数组 `.max(256)` 溢出（ZodError，曾以同样方式卡住 C2） | 一夜 |
| 验证未提交 | 观测隧道断裂，「sign-in failed」无原因 | 一夜 |
| 第三轮耗时一天 | 每次增量 = 全部行为 × 图片证据 × 两遍 | 结构性 |

**根因：系统没有容量模型。** 修任何单点都不能阻止下一个独立常数被撞出。

实测数据（本仓库真实运行）：

- 计划规模：贪吃蛇 14 条，计算器 C3 41–45 条
- 一次增量端到端：约 30 分钟，其中生成约 10 分钟、验证操作约 20 分钟
- 评审器单遍工具调用：150–240 次；证据条目：42 条行为 > 256 项（触发溢出）
- 修复记录阶段死循环后：拒绝次数 4 → 0，42 条行为全部记录完成

## 2. 目标 / 非目标

**目标**

1. 任何计划在花第一个模型 token 之前，其资源包络被计算并验证；超限要么自动分批、要么带具体数字拒绝——绝不在运行中途撞墙。
2. 每次增量的验证成本从「全部行为 × 两遍 × 图片证据」降为「受影响子集 × 一遍，非视觉行为用文本证据」；全量五组检查保留为发布门禁与周期安全网。
3. 任何失败的真实原因以结构化形式落库并在工作台可见；笼统文案只允许出现在用户提示层。

**非目标（红线）**

- 不减少五组完整子检查；它从「每次增量」挪到「发布门禁」，内容一字不改。
- 不让 agent 改写断言或判定标准（行业红线：断言变更必须人类所有）。
- 不取消视觉行为的图片证据要求。
- 不改变生成器/协调者的产出质量要求（#45 的 builder 规则继续推进，正交）。

## 3. 总体设计

### 3.1 不变式 I：容量模型（`capacity.ts`）

新建 `apps/api/src/runtime/capacity.ts`，**成为所有限额的唯一来源**。

```
costPerBehavior = { toolCalls: 6, evidenceEntries: 7, imageTokens: ~1500, seconds: 30 }
envelope(N)     = N × costPerBehavior × headroom(1.5) + overhead(20)
limits(N)       = max(硬下限, envelope(N))
```

现有常数（`REVIEW_TOOL_LIMIT`、`RUN_TOOL_LIMIT`、`REVIEW_EVIDENCE_LIMIT`、`RUN_IDLE_TIMEOUT_MS`、租约分段等）全部改为从 `limits(计划行为数)` 推导；孤儿常数禁止新增（lint 规则或 code review 检查点）。

**跑前预检**：协调者产出计划后、第一个模型调用前：

1. 计算 `envelope(N)` 对照各限额；
2. 包络可分批 → 自动把行为切成 `ceil(envelope/limit)` 批，逐批评审、合并 verdict；
3. 不可分批（单批就超硬下限）→ 带具体数字拒绝：「45 条行为约需 270 次调用，预算 280/批，已超出单次能力，建议拆分需求」；
4. **影子模式先行**：第一版只记录「若执行会拒绝/分批什么」，与真实运行对照一周，校准 `costPerBehavior` 后再切强制执行。

### 3.2 不变式 II：分层验证

| 层 | 时机 | 范围 | 证据形态 | 成本 |
|---|---|---|---|---|
| A | 每次增量 | 受影响行为 + 底线集 | 可访问性树文本（确定性断言，无模型） | 秒级 |
| B | 每次增量 | 真视觉行为（`requiresVisualEvidence`，已实现） | 模型 + 已投递图片 | 分钟级 |
| C | 发布门禁 / 周期 | **全量五组，一字不改** | 现状 | 小时级，不挡路 |

**行为分类信号**（保守原则：判不准就升级，绝不漏验）：

- 视觉判定：`requiresVisualEvidence(target)`（已实现于 `feat/44-text-evidence`，fail-closed）；
- 受影响判定：代码 diff → 行为映射的启发式 v1（行为 target 提及的控件/文本与改动文件相关）；**判不准一律纳入**；
- 底线集：协调者在计划中标注（首渲染、主流程、持久化、账号隔离），无标注时取固定小集。

**召回度量**：新表 `check_coverage(run_id, behavior_id, tier, verdict, skipped)`。C 层每次运行时，统计「A/B 层跳过但 C 层判失败」的行为数；召回率 < 100% 持续出现 → 自动扩大子集（先加底线集，再全量）。这是行业「子集+安全网+召回」的标准做法，**断言标准不下放**。

**与 #44 分支的关系**：`feat/44-text-evidence` 的谓词与门控改造即 B 层的证据形态变更；17 个失败测试逐个判定（每个标注「固化旧行为」或「真实保证被破坏」），不批量改期望。

### 3.3 不变式 III：错误是数据

- 新表 `run_failures(run_id, phase, code, detail_json, cause_class, created_at)`；
- `executor.ts` 兜底分支**必须**写入此表（现在只 `console.error`）；ZodError 映射为 `SCHEMA_VALIDATION` + `issues[0]` 摘要；
- 工作台运行视图显示 `detail_json`；用户提示文案保持笼统，但**任何失败不再需要进行日志考古**；
- 验收：人为注入一个 ZodError，UI 显示「评审证据超过 N 项」而非「生成或保存未完成」。

### 3.4 运维改造

- 诊断一律单条 SSH 命令在服务器就地完成（无长连主连接可断）；
- 中期：带鉴权的运营只读端点 `GET /api/v1/ops/runs/:id`（运行状态+最近事件+run_failures），分诊不再依赖 SSH；
- 部署流程不变（已可靠），保留磁盘水位检查与保留上限。

## 5. 风险与回退

| 风险 | 缓解 |
|---|---|
| 行为分类假阴（漏验真缺陷） | 保守默认（判不准就纳入）+ 召回度量 + C 层周期全量 |
| 容量模型失准 | 影子模式校准一周后才强制执行 |
| 分层开关复杂度 | 单一环境变量；C 层永远可用、永远权威 |
| 改造期破坏现有能力 | 全部改动进分支；P1/P2 部署以 C3 基线完成为门禁；372 个 API 测试保持全绿 |
