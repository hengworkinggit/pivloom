# 已发布应用的数据边界

源码版本、Preview 示例数据和线上业务记录是三种不同资源。

- Preview 的四类交互模板数据只存在该浏览器中；更换浏览器或源码版本不会自动迁移示例数据。
- 发布后的报名和预约由同域 `__pivloom/data` 接口写入 PostgreSQL，记录按 `owner_id + project_id` 隔离。它们不属于沙箱，也不随源码版本切换或回滚而删除。
- 公开访客只能提交报名、预约以及读取不含身份信息的已占用时段。项目主人通过已认证的工作台接口查看、确认、删除和导出记录。
- 读书清单和任务看板属于项目主人的个人数据。发布页面的静态文件和数据接口都要求主人从已登录的工作台授权打开；其他账号或匿名访客不能读取、写入。授权交换为该项目域名设置 HttpOnly Cookie，不把 Pivloom 密码或登录令牌交给生成的应用代码。Cookie 绑定项目和当前登录会话；退出登录、会话失效或授权过期后访问被拒绝。
- 个人模板采用项目专属服务端状态，保存时校验版本；另一页面已经修改过时返回冲突，避免静默覆盖。项目 A 与项目 B、账号 A 与账号 B 的数据在数据库中按所有者和项目隔离。源码版本变更与数据生命周期分离。
- 服务端验证字段、限制每项目 10,000 条和每小时 1,000 次提交；数据库唯一约束防止重复报名及同一日期时段的并发重复预约。浏览器不持有数据库密钥。
- 发布资格和回滚资格由同一个 `nano.revision_eligible` 规则判断。托管数据项目额外要求当前源码具有有效的 `pivloom.data.json` 和运行时数据模块；旧的本地版模板需要重新创建或增量升级后才能作为在线报名、预约应用发布。
- 发布复制的是静态代码。线上业务数据从不复制回 Preview，Preview 示例数据也不会在发布时进入线上。发布时的代码版本和生产数据生命周期独立。

当前托管数据覆盖活动报名、预约排期、个人读书清单和个人任务看板。新模板发布后使用服务端数据；旧版已发布的个人模板没有自动迁移到新数据区，需要升级源码并重新发布，其浏览器旧数据也不会自动导入。任意生成应用的通用动态数据模式、文件上传、自动通知和离机备份仍未提供。数据已具备跨服务重启和代码版本切换的持久性，但不能据此承诺服务器损坏时零数据丢失；正式对外承诺恢复能力前必须配置备份和恢复演练。

验收时至少覆盖：两个浏览器提交后主人都能看到；公开接口不能列出联系人；两个并发请求争夺同一时段只有一个成功；重复请求标识只创建一条记录；个人模板只有主人授权后可打开，另一个账号与匿名浏览器无法读取静态页面或数据；退出登录后既有 Cookie 失效；个人数据更新冲突显式报错；重启 API、发布新代码和回滚源码后记录仍在；模拟数据接口故障时发布页阻止提交而不是回退到本地存储。
