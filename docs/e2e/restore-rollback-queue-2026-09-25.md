## 为什么这一条以前不通过

需求 2 要求生成、增量、重试、**预览恢复**与**历史回滚**共用同一个调度器与容量账本。此前生成会排队，而恢复与回滚在容量满时抛 `SERVICE_BUSY`——请求根本没有落库，也没有任何机制稍后启动它。

## 实现

- `migrations/022`：`nano.preview_restores` 增加 `queued` 状态；`nano.claim_next_queued_restore` 在预约到名额的同一事务里把行改为 `pending`，执行器无需改动即可消费。
- `migrations/023`：`nano.rollbacks` 同样增加 `queued`，`nano.claim_next_queued_rollback` 改为 `preparing`。
- 准入是原子的：预约只在它自己的事务里有效，所以「begin 里预约、稍后建沙箱」会留下窗口让另一个操作也看到一个空名额。`nano.reserve_restore_slot` / `nano.reserve_rollback_slot` 在与计数函数同一把咨询锁下**决定并插入**，`nano.generation_capacity_occupied` 统一计算「已占名额」——包括已准入但尚未登记沙箱的恢复与回滚，此前它们对计数完全不可见。

## 一个顺带修掉的真实缺陷

`claim_next_queued_run` 原先按「位次」排序，而两行的位次可能相同（键不同但计数相同）。位次并列时 `LIMIT 1` 把选择权交给了物理行顺序——**一个已经被服务过的账号可能抢在等待中的账号前面**，正是这个队列要防止的饿死。派发现在按产生位次的同一个键排序，两者不可能再分叉。该修正放在 023 中，因为 021 已在生产应用、迁移工具拒绝变更已执行文件的内容。

## 本轮未覆盖（NOT_RUN）

- **回滚排队在真实页面上的观测**：本项目当前的测试项目没有「两版均已验收且可回滚」的组合，构造它会消耗一次真实生成的额度与沙箱，属 #37 冻结主线的资源。回滚排队由真实 PostgreSQL 集成测试覆盖（8/8）。
- **恢复排队时的页面状态观测**：本次触发恢复时该版本仍有可用预览，页面按设计优先显示可用预览而不是等待文案；等待文案只在没有可用预览时出现，其渲染由前端组件测试覆盖。要在页面上同时看到「排队中」需要一个已过期预览加满容量，代价是再占一次沙箱，留待 #37。

## 上线过程里的一个有用发现

切换 API 时部署脚本**正确拒绝**了发布：`{"activeOrUncleanRuns":0,"retainedSandboxes":2}` —— 本节验收占用的两个预览仍占着名额，脚本要求环境空闲后才允许切换。释放这两个预览（本次验收的收尾）后重试即成功。这说明「保留预览属于占用、发布前必须空闲」这条保护是真的在起作用，不是纸面规则。
