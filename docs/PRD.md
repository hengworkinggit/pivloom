## 1. 产品目标与任务边界

交付一个可以在线使用的 AI Web 应用构建工作台。用户用自然语言提出需求，系统在远程沙箱中生成真实多文件代码，运行应用并提供可操作的预览；用户可以在同一项目连续修改，离开后再回来继续。

选定的延展是固定三角色协作：协调者明确目标，工程师实现，检查者实际操作生成应用；检查发现具体问题后交回工程师，最多两轮修复。用户获得可使用的结果和简短状态，不需要阅读长篇验收报告。

**最终目标范围是 P0 + 选定 P1。P0/P1 表示实现顺序；没有完成 P1 时必须如实说明，不能把三个头像或静态日志称为已实现协作。** P2 不进入本轮工期承诺。

### 1.1 题面要求、我们的选择、未来范围

| 层次 | 本轮解释 |
|---|---|
| 题面明确要求 | Agent 驱动生成、可视化呈现、真实交互、数据持久化、在线 Demo、GitHub 源码和提交文档、收题后 48 小时提交 |
| 条件性或建议项 | 注册等扩展流程、至少一种延展能力、6–8 小时集中开发建议、取舍说明；不改写成逐项硬性评分细则 |
| 我们主动确定的质量目标 | 同项目两次追加修改、真实源码视图、取消与重试、失效沙箱重建、固定三角色与浏览器检查 |
| 本次不承诺 | 复制全部 Atoms 菜单、每个生成应用的通用后端与永久发布、完整多团队或模型路由/计费平台 |

持久化落实为服务端保存项目、聊天、源码快照和结果。生成应用的业务数据可在示例中用 localStorage；此时必须说明它只属于该浏览器/预览来源，不宣称有云数据库或跨设备同步。部署要求落实为**Pivloom 工作台上线**；生成应用得到可恢复的临时预览，不宣称永久托管。

依据是[原题逐项核对 R01–R12](../research/brief-requirements-recheck.md)。这是我们对题目的落实方式，不冒充评审方未公布的测试规则。准确收题时刻未知；工期安排见 TRD 的实施路线。

## 2. 用户、核心场景与成功标准

### 2.1 用户

- **评审/体验者**：拿到地址与受限测试账号，独立创建应用、操作预览、继续提出修改。
- **构建者**：想迅速做一个可交互的前端原型，关注结果和修改是否有效。
- **开发维护者**：需要定位失败阶段、查看源码、日志和特定版本的检查结果。

本轮不设计组织管理员、计费管理员、多人同时编辑、应用终端用户账号体系。

### 2.2 必须成立的核心场景

1. 新建“活动报名管理”项目，输入需求，得到表单、列表和筛选实际可用的应用。
2. 在同一项目提出“增加状态筛选”，再提出“增加统计和窄屏布局”；既有新增与校验行为仍可用。
3. 刷新工作台、退出后重新登录，项目、需求、结果和真实源码仍在。
4. 预览沙箱过期时点击恢复，系统从服务端快照重建，不要求用户重新描述应用。
5. 看见工程师完成后检查者实际操作表单；另用可复现缺陷验证失败→修复→复查的流程。
6. 更换成“读书清单”需求，产生相应实现，证明不是预制页面切换。

### 2.3 发布完成定义

| 维度 | 完成定义 |
|---|---|
| 生成真实性 | 至少两个不同的新需求走真实模型和远程工具，源码与要求对应；空白模板可预置，成品不能按需求类型切换冒充生成 |
| 连续开发 | 一个项目完成初次生成和两轮修改；每轮检查新增行为及至少一个已有行为 |
| 交互 | 在预览里实际输入、点击、提交或筛选；HTTP 200、截图和构建成功本身不算行为通过 |
| 持久化 | UI 重新打开能恢复；服务重启和沙箱失效分别验证，不把 localStorage 当平台存储 |
| 协作 | 独立角色 session、不同工具权限、带版本的结果交接；检查失败有真实修复分支 |
| 可交付 | 外部可访问工作台，源码和运行说明齐全，所有未实现能力明确列出 |

本轮没有统计样本足以承诺“成功率 95%”。记录两套需求的实际结果、耗时和用量；不把小样本体验外推为性能指标。

## 3. Atoms 对标与差异化

Atoms 官方资料确认了项目聊天、单 Agent/Team Mode、交互预览、代码、历史、视觉编辑、Cloud 和发布等能力。我们对齐其中一条完整开发路径；未登录 Atoms 做全面 E2E，官方描述与实测结果分开记录。[功能核验](../research/atoms-feature-audit.md)

| Atoms 能力 | Pivloom 本轮实现 | 明确不包含 |
|---|---|---|
| Project Chat | 文字需求、真实活动、持续修改、停止/重试 | 附件、语音、复杂消息队列管理 |
| Team Mode | 固定协调者/工程师/检查者，按阶段交接 | 任意建队、成员管理、跨团队、Race |
| App Viewer | 可操作 iframe、刷新、新标签、桌面/窄屏、失败提示 | 浏览器直播、同屏接管、多页面管理台 |
| Code and files | 实际快照的文件树与只读内容 | 手动代码编辑、可写终端 |
| History | 服务端保存版本与结果 | 完整历史页、Remix、数据库回退；恢复旧版本 UI 为 P2 |
| Design | 聊天描述修改 | 元素点选、拖拽和属性面板 |
| Cloud | 仅工作台自己的身份与项目持久化 | 每个生成应用开库、认证、迁移和环境管理 |
| Publish | 工作台在线；生成应用临时预览可恢复 | 生成应用永久域名、发布审批与更新渠道 |

我们的差异化假设是：**把“生成完”推进到“关键操作试过，发现问题能修”**，并让用户看懂当前由谁处理。固定小队提供可观察的分工，不以角色数量作为价值。Multica 是协作机制参考，Pi 是执行底座，均不代表整个方案是市场首创。

“每个版本都有可复查证据”只作为内部实现原则。默认结果卡最多展示改动摘要、检查状态、一个问题摘要和下一步。工程师可展开查看检查步骤、截图和日志；普通用户不必审阅它们。若检查耗时、成本明显超过减少的返工，后续再评估缩减自动检查范围，而不是先扩展为证据平台。

## 4. 功能需求

### F01 · 受限评审入口 · P0

提供账号密码登录和退出，由维护者预建测试账号。错误信息不区分账号不存在与密码错误。无效或过期登录不能调用模型、读取其他人的项目或获取快照。刷新会话失效时回到登录，并保留可安全保留的未发送草稿。

本轮不做自助注册、找回密码、邀请、社交登录。公开成果链接不等于工作台应允许匿名无限消耗模型；提交说明给出评审可用入口。

**验收**：有效账号进入；错误凭据得到明确反馈；退出后受保护页面不泄漏内容；A/B 两账号互不可读写项目。

### F02 · 项目创建与重新打开 · P0

项目列表包含标题、更新时间和最新结果状态；支持创建与打开。创建后生成独立项目 ID，空项目给出文字输入和两个示例提示，示例只填入输入框，不直接生成成品。项目标题可从初次需求生成短标题，也可先用“未命名项目”，不增加重命名管理流程。

本轮不做项目删除、文件夹、共享协作、复制和搜索。没有项目时不能出现看似可点但无实现的项目卡。

**验收**：连续创建两个项目，相互隔离；刷新列表后仍在；打开指定项目能找到自己的历史与结果。

### F03 · 从需求生成应用 · P0

输入 1–8,000 字符文字，去除首尾空白后提交。空文本阻止发送；超长文本在提交前说明。成功接受需求后，显示持久化的用户消息与任务状态，输入框清空；服务忙碌、网络失败或未接受时保留输入。

系统基于统一的 React/TypeScript/Vite 空工程生成多文件应用，真实读取/写入/安装/构建。生成应用只承诺前端原型能力。遇到支付、跨用户数据库等范围外需求，协调者解释限制并提出前端演示实现；不能静默模拟真实付款或登录成功。

需要决定关键业务语义时，可提出一个简短澄清并结束为“需要补充信息”。用户回复后创建后续任务。普通颜色、布局等可逆选择由系统作合理默认，避免每一步要求批准计划。

**验收**：新需求产生相应实际源码与行为；构建失败不能显示完成；实际模型/工具记录可追溯到 run ID。

### F04 · 可理解的执行过程 · P0

显示正在明确需求、准备环境、编写代码、构建、检查、修复、保存结果等实际阶段，禁止假百分比。活动条显示角色和简短动作；工具明细默认折叠，包含文件名、命令类型、结果和截断日志，不展示模型内部推理。

断开事件连接显示“连接中断，正在重连”；任务是否停止以服务端为准。刷新工作台后从服务端恢复当前状态，不能重新发起同一需求。模型输出的“完成了”不能直接驱动完成状态。

**验收**：页面状态对应真实事件；刷新不重复执行；连接恢复后活动不重复、终态不倒退。

### F05 · 可交互预览 · P0

预览区显示被查看的版本以及“检查中/检查通过/存在问题/尚未检查”状态。支持刷新当前应用、在新标签打开相同版本、桌面宽度与 390px 窄屏容器切换。工作台本身在较窄屏幕改为聊天/预览标签，保留输入和停止按钮。

用户可在预览内真实点击、输入和提交。首次生成时有清晰空态；新任务期间仍可查看上一个成功版本；新候选版本和旧版本不能共用会被改写的运行目录。构建未成功不暴露半成品 iframe。

产品内部检查者的 Chrome 与用户 iframe 是**两个会话**，不得声称能看到用户当前表单内容或接管用户页面。新版本可能使用新预览来源；生成应用 localStorage 数据不承诺跨版本迁移。

**验收**：iframe 内关键操作成立；打开的新标签与所选版本一致；候选检查不能误标旧页面；过期地址给出恢复入口。

### F06 · 同项目持续修改 · P0

一次任务结束后，用户在原项目追加需求。新任务基于当前成功快照和项目上下文进行增量修改；初次未通过检查时，可以重试待修复候选。每次保留原需求与结果，不创建一堆无关联项目。

同项目同时只有一个运行中的生成/修复任务。执行中仍可输入草稿，但发送禁用并说明“当前任务结束后可发送”；第二标签或重复请求由后端返回冲突，不静默吞掉新输入，也不偷偷排队。修改成功后切换到新版本，旧快照仍保留在服务端。

**验收**：同项目完成两轮修改；原有关键行为回归通过；并发提交只接受一个新任务，另一个保留草稿。

### F07 · 平台持久化 · P0

服务端保存项目、用户需求、结果消息、任务终态、角色产物、源码快照和检查记录。页面刷新、登录会话变化、服务重启、OpenSandbox 过期不应导致已确认保存的项目资产丢失。

保存成功只能在源码对象上传完成、校验通过、数据库结果提交完成后显示。持久化失败时显示失败及重试，不把浏览器缓存或仍存活的沙箱当成已保存。未保存的流式日志最后一个小批次不保证崩溃后完整恢复，已提交需求和结果不受这个限制。

**验收**：重新登录后需求和源码一致；使沙箱失效再重建，得到相同源码内容；写存储失败不能产生虚假的成功版本。

### F08 · 只读源码 · P0

预览旁提供“代码”页签，展示所选版本的真实文件树、文件路径和文本内容。源码来自已保存快照，默认打开应用入口文件；显示版本 ID，不能给最新预览配上另一个版本源码。

没有快照时显示空态；未选文件时给出提示。长文本可滚动，不能影响工作台整体布局。排除依赖目录、编译产物、密钥文件和宿主路径。没有编辑、保存代码、运行任意终端等入口。

**验收**：需求中的功能可以在实际文件中找到；刷新后内容不变；不得读取其他项目或任意路径。

### F09 · 停止 · P0

运行时提供停止按钮。点击后先显示“正在停止”，服务端取消模型调用、远端命令与浏览器活动并拒绝后续交接；确认清理完成后显示“已停止”。如果远端状态无法确认，明确显示清理待确认并暂时禁止该项目再次生成，不显示假停止。

停止不撤销用户此前已提交的结果。取消中的候选版本不能成为当前成功版本。页面刷新后仍显示同一个停止状态；重复点击停止是幂等操作。

**验收**：模型阶段和命令阶段各验证一次；停止后不再有新写入、角色派工或新版本发布；上一成功预览仍可用。

### F10 · 失败与重试 · P0

区分模型/认证、安装/构建、预览启动、浏览器基础设施、行为检查、保存与运行中断。给出用户可理解的简短原因和可执行动作；详细错误在展开区带 run ID。

“重试”创建新 run，链接旧失败 run，并沿用其需求及可用输入快照。失败记录保留；不得把旧 run 重置为运行中。重试不保证完全相同输出；界面不承诺透明续跑。

预算或修复上限达到时停止并说明，不无限调用。浏览器不能访问属于“检查受阻”，不能记为检查通过，也不应直接判断业务实现错误。

**验收**：模型错误、构建错误、存储错误和重启中断都有真实失败表现；可以按适用路径重新尝试。

### F11 · 恢复失效预览 · P0

页面打开项目时服务端判断预览是否仍有效；失效时显示“源码已保存，预览需要重新启动”，可触发恢复。恢复从所选已保存版本创建新沙箱、还原代码、安装锁定依赖、构建并启动，不调用生成模型、不产生新的源码版本。

重建期间有状态提示；失败可重试。恢复得到新 URL 后更新 iframe。它只恢复代码与可运行页面，不恢复 Chrome 内存、用户 iframe 的表单状态或生成应用的 localStorage。

**验收**：强制过期后通过 UI 恢复；源码哈希与原版本相同；模型调用次数没有增加。

### F12 · 在线交付 · P0

上线的是完整工作台及常驻 API，连接真实模型、OpenSandbox、数据库和对象存储。评审无需启动本机服务。提交源码仓库、运行/部署步骤、环境变量名称、测试入口和已完成/未完成说明。

公开仓库不包含模型密钥、测试账号密码、私人题面全文及联系人。按题面处理成果访问权限；飞书个人副本、署名与发送提交属于之后的交付动作，本次文档编写不代替用户提交。

**验收**：线上从登录到生成及重新打开可走通；仓库从干净环境可按文档启动；链接权限实际核对。

### F13 · 固定三角色真实协作 · P1，选定延展

协调者输出简短目标与 1–5 个可观察行为；工程师实现；检查者对具体候选版本进行浏览器检查。初次生成和普通追加修改均执行这条固定流程，重试可复用已有效保存的计划，但需如实标记“沿用计划”。

三个角色各有独立 Pi session 和受控工具集，可以共用同一模型。协调者不能改代码，检查者只能读源码并操作测试浏览器，工程师是唯一写源码者。工具权限由服务端限制，不能只靠角色 prompt。

每次交接保存来源、目标、任务、输入版本和结果摘要。界面显示实际发生的角色活动；没有执行的阶段不补造动画或消息。固定流程不开放普通聊天 mention 派工。

**验收**：审计记录存在三个独立 session；未授权写工具被拒绝；检查操作和报告都关联同一版本；成员结束不等于总任务完成。

### F14 · 浏览器检查与有限修复 · P1，选定延展

检查者执行计划中的关键行为，并包含至少一个真实用户动作和一个结果观察。结果分为通过、失败、受阻；每项记录预期、实际和必要截图/日志。不得仅凭模型文字、构建通过或页面存在标题判定全部通过。

可修复的行为/构建失败最多交回工程师两轮；每轮得到新候选快照，重新构建并检查。最后仍未通过则保留候选和问题摘要，任务终态为“仍有问题”，上一个成功版本保持不变。首次生成无成功版本时，可查看构建通过且预览可用的带警示候选；不能显示检查通过。构建仍失败的候选只提供问题与源码，不提供假预览。

默认结果卡示例：

> 已增加状态筛选。新增、筛选和原有表单校验已检查。打开预览试用；检查详情可展开。

失败卡示例：

> 筛选仍未通过：选择“已完成”后列表未变化。已尝试修复两轮。上一成功版本仍可使用，可补充要求后重试。

**验收**：正常路径不强制制造缺陷；另外运行可复现的缺陷夹具，证明检查失败、修复、复查的实际链路；报告不可被迟到的旧版本结果覆盖。

### F15 · 用户模型设置 · P0

登录用户从设置页面填写Provider、Base URL、API Key、模型名称，实际测试连接并保存；支持编辑、更新密钥、设默认和删除。重新登录后仍可使用，页面只显示密钥掩码。每个账号使用自己的配置；工作台选择模型，每次任务固定配置版本。普通用户无需修改环境文件；模型通信继续复用pi-ai。

**验收**：E31完成新增→错误反馈→真实连接→保存→重登→更新/默认切换/删除，I12验证owner、加密与URL目标限制；DEV-03再验证所选模型确实用于生成。无配置引导设置，不自动借用其他账号密钥。

## 5. 页面与交互结构

### 5.1 页面

| 页面 | 必备元素 | 主要状态 |
|---|---|---|
| 模型设置 `/settings/models` | 服务名称、Provider、Base URL、API Key、模型、测试/保存/编辑/默认/删除 | 无配置/编辑中/测试中/可用/失败 |
| 登录 `/login` | 账号、密码、登录、错误提示 | 空闲/提交中/失败 |
| 项目列表 `/projects` | 新建项目、项目卡、退出 | 加载/空列表/有项目/失败 |
| 工作台 `/projects/:id` | 项目标题、聊天、角色活动、输入、停止、预览/代码页签 | 未生成/运行中/成功/需补充/有问题/失败/中断 |

桌面采用聊天与结果双栏；侧栏可简化为返回项目列表。不要复制 Atoms 全部导航以填满页面。工作台优先支持 1280×800；窄于 900px 时用聊天/结果切换避免双栏挤压。390px 的应用预览与 390px 的工作台测试是两项不同检查。

### 5.2 结果区状态

| 状态 | 展示 | 用户动作 |
|---|---|---|
| 无结果 | 空态与需求示例 | 输入需求 |
| 正在生成 | 当前阶段；有旧成功版本则继续显示旧版本和版本号 | 停止、编辑草稿 |
| 候选检查中 | 候选卡显示版本与“检查中”，旧成功结果不被冒充替换 | 查看候选或旧结果 |
| 完成 | 新成功版本、改动摘要、简短检查结论 | 实际试用、继续修改、看源码 |
| 仍有问题 | 失败行为和修复次数；有旧结果则默认留在旧结果 | 看候选问题、重试 |
| 失败/中断 | 阶段、原因、run ID | 重试或恢复预览 |
| 需要补充 | 一个可回答的问题，任务不再持续占资源 | 输入回复 |

每个按钮必须有实际实现；未做的发布、数据库、团队设置和素材库入口不出现。键盘提交采用明确规则：Enter 发送，Shift+Enter 换行，中文输入法 composition 期间 Enter 不触发发送。

## 6. 非功能约束

- **真实状态**：服务端状态为准；持久化、构建与检查分别表示，不能互相替代。
- **可控资源**：单项目串行、全局并发限制、每次任务时间/工具/Token 上限；限制数值见 TRD，须在首次集成后校准。
- **数据隔离**：所有项目、源码、事件、截图接口核验 owner；生成应用与工作台不同来源；模型密钥只在可信服务。
- **可恢复**：已保存源码独立于沙箱；进程中断可重新尝试，不承诺不中断地恢复模型执行栈。
- **可读性**：主界面中文，术语尽量转成“编写/构建/检查/保存”；原始日志折叠；错误用正常文字说明下一步。
- **可访问性**：输入有 label、按钮有名称、错误有可读取状态；停止和重试支持键盘操作；不只用颜色表示失败。
- **可诊断**：用户可复制 run ID；维护者能关联版本、角色、工具、耗时和用量；不暴露密钥或隐藏推理。

## 7. 明确延期

P2 仅在全部核心用例通过且有余量时评估：前一版本恢复 UI、生成源码 ZIP。

以下不进入本轮：自助注册/计费/团队权限；任意多 Agent 和并行 Race；Visual Editor/素材/附件输入；手动源码编辑/PTY；GitHub OAuth 同步；应用永久发布/自定义域名；每应用 Supabase 与 dev/prod；连接器/Research/模型市场；原生移动/视频；SEO/Ads/Analytics；浏览器直播/远程接管；分布式任务队列/透明恢复/完整追踪平台。

不把这些做成无效占位入口，也不把基础工作台存储称为“已实现 Atoms Cloud”。

## 8. 风险、验收与变更规则

最大的技术风险是 Pi 远程工具、OpenSandbox Chrome、预览和模型效果能否在所选环境串起来；TRD 的 G0 必须先验证。当前已完成的研究和浏览器夹具试验不能替代这个集成门槛。

完整验收执行 [E2E](E2E.md)：P0 流程全部通过；F13/F14 若作为已交付延展，也必须通过相应正常及故障用例。无法执行的检查标为 BLOCKED，未执行标为 NOT_RUN，不能按推断记 PASS。

若实际剩余时间不足，先删除 P2 和所有延期项；P0 阻塞优先修复。需要进一步缩减选定 P1 时，必须更新完成清单并明确告知，不在代码或演示中偷偷用静态结果代替。实现过程中新增功能必须能指向本 PRD 编号，否则先进入后续清单。
