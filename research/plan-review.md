# Fragments 主底座方案独立审查

基于根代理已核实的 Fragments 特性审查，不新增搜索、不声称做过运行验证。

结论：**方向成立，条件是明确“一个固定 Next.js 模板中的单文件交互页面”这一交付边界。** 它比 8 小时内再拼通用 coding agent、编辑器、沙箱更可交付。Pi 后续再替换 Runner 很合理；此阶段不用同时集成 Pi、DSH、Codex。

## 1. 持久化保存错对象：只存聊天仍会丢作品

风险：Supabase projects/messages 解决的是外层生成器历史；沙箱是计算环境，不能作为唯一代码仓库。若题面“持久化”也包含生成应用自身的业务数据，仅存 generator 的历史不能算完成。

收敛：至少分清三类东西，不把它们都叫“保存”。

- **控制数据**：projectId、message、revisionId、parentRevisionId、状态、当前选中版本。
- **作品数据**：每版本不可变的确切源文件（本次可直接 code_text）、templateVersion/dependency lock 标识、build/browser 结果、截图引用。这些保存在数据库/对象存储，sandboxId 仅是可失效运行位置。
- **生成应用业务数据**：只有所选示例需要跨刷新/跨设备保留任务或记录时才要求独立数据方案。8h 不做通用动态数据库生成；明确限定本次模板类型，或选一个预置 CRUD schema 的示例。localStorage 只能说明同浏览器保留，不能叫云端持久化。

最小写入顺序：create pending revision → 保存代码 → 执行 build/verify → 保存实际结果/截图 → 标记 validated 或 failed。刷新后从 revision 恢复，不从聊天重新推测源代码。失败版本也可保留诊断，但不要成为“最后成功版本”。

## 2. 验收自证：模型说通过、截图好看都不是功能通过

风险：同一模型生成页面、生成测试、解释通过，容易把同一误解重复三遍。截图只能证明某一时刻的外观，不能证明数据、交互或持久化。

收敛：先冻结验收项，再生成代码；验收项必须能对应真实动作和观察。采用固定由产品维护的 Playwright 测试骨架，或用户可见并可编辑的少数断言参数。比如“新增任务→出现该任务→刷新→仍存在”，而不是检查源码含有 Todo 或页面出现按钮。构建成功、页面加载、console/pageerror、用户流程分别记录，展示真实 pass/fail/未执行，不把未执行算通过。

同一模型仍可以读错误并修复，但**判分器与修复提示分开**：修复代码后运行原验收项，保留失败日志，不因为修复过程困难自动降级标准。验收报告绑定 revisionId 与文件 hash；旧版本报告不能复用于新代码。

## 3. 稳定评审链接 ≠ 沙箱永远运行 ≠ 永久部署

风险：Fragments 原生 publish 的 TTL+短链只能延长并包装临时预览。把它标成“已上线、永久可用”会在评审过期后直接失败。

收敛：应用自己提供 `/p/:projectId/r/:revisionId` 稳定评审地址。此页展示已存源代码/截图/验收结果，live iframe 指向当前 sandbox；沙箱失效后从已存版本重新启动，显示“正在恢复预览”。稳定的是版本与评审入口，不承诺 sandbox 永不停止。部署后的公开站点若题面明确要求，则加独立构建产物发布流程；本次不要把“生成器已在线可体验”和“每个生成应用永久托管”混为一谈。

8h 的最低可兑现路径：生成器公开 URL + 稳定 revision review URL + 可重建的临时 live preview。若重建耗时长，先显示截图/结果并给出明确恢复状态。

## 4. Agentic 只是话术：streamObject 换一个提示词不够

风险：保留一次性结构生成，再用相同 prompt 重生成一次，缺少真实环境反馈；界面动画也不能补足。反过来，临时引入通用多文件 agent loop 会挤掉交付时间。

收敛：把生成器构造成最小有界行动循环：冻结目标/验收 → 生成文件 → 写入 sandbox → 真实 build/浏览器执行 → 读取结构化失败证据 → 模型基于 evidence 改代码 → 再 build/verify → 交付成功或如实失败。最多一次自动修复是合理预算；关键是第二次输入包含实际错误、当前源代码和原验收标准，而非重复自然语言需求。

这能形成清晰的观察反馈闭环；不必伪装开放式自主 Agent。为后续保留 Runner 接口足够，不为抽象而现在装 Pi。多轮修改时把**选中 revision 的完整代码**作为上下文，不能只传聊天摘要，也不能把每轮新沙箱说成连续原地编辑。

## 5. 8h 超支：底座可运行不等于完整产品已集成

风险最大增项：框架版本升级、从单文件改多文件、通用生成数据库、登录权限系统、永久发布、多 Agent、任意依赖安装、复杂差异编辑器。每一个都可能吃掉验证时间。

收敛：锁底座依赖与单一模板，固定 npm dependencies，只生成一份受控文件，每个版本全量快照，单人演示流程，三栏或两栏现有 UI 不大改。Supabase/E2B credentials 与线上部署必须在第一小时验证，不能留到最后。保留至少 90 分钟真实端到端演示、失败分支和文档。

建议 8h 上限预算：

- 0–1h：原版跑通、模型/E2B/数据库/线上部署连通；若无法跑通即缩范围。
- 1–2.5h：固定模板生成、多轮带代码上下文、项目/版本/聊天落库与恢复。
- 2.5–4.5h：真实 build + 最小浏览器验收 + 一次反馈修复。
- 4.5–6h：绑定版本的验收/截图、稳定评审入口、失效预览重建。
- 6–8h：新项目生成→一次修改→刷新恢复→浏览器验收→分享链接全流程；失败/超时如实呈现；部署与 README。

如果只剩 6h，优先保留代码/版本持久化、真实执行反馈、可访问评审入口；验收项只做 2–3 个；不要牺牲这些去做模型切换、多 Agent、组件市场或“永久部署”包装。

## 推荐写入主报告的一句话

我们借 Fragments 解决生成与预览的基础设施，创新点放在“**每个版本都有可复查的用户验收证据，失败会根据真实运行结果自动修一次，版本可恢复且评审入口稳定**”；不把聊天框、沙箱或框架拼装本身称作创新。
